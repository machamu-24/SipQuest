# SipQuest 企画書

## 1. 文書概要

- 文書名: SipQuest 企画書
- 作成日: 2026-03-31
- 対象: プロダクトオーナー、開発担当、デザイナー、運用担当、協力パートナー
- 対象プロダクト: SipQuest
- 文書目的: 現行アプリの実装内容を踏まえ、SipQuest を個人向け飲酒ログアプリとしてどのように位置づけ、どのように拡張・運用していくかを整理する

## 2. エグゼクティブサマリー

SipQuest は、日本酒、ハイボール、ビール、ワイン、その他の飲み物について、飲んだ日、銘柄、産地、味メモ、写真を記録し、地図から振り返れる個人向けログアプリである。単なる記録アプリではなく、「飲んだ体験を地理情報とともに思い出す」ことを中核価値に据えている点が最大の特徴である。

現行の実装は、Next.js ベースのモバイル志向 Web アプリ兼 PWA として構築されており、記録の作成・検索・詳細閲覧・編集・削除、写真保存、日本地図/世界地図での地域別閲覧、ホーム画面追加に対応している。一方で、認証、クラウド同期、CSV エクスポート、分析ダッシュボード、レコメンド、共有機能などは未実装であり、現段階では「個人利用を前提とした地図型テイスティングノート MVP」と位置づけられる。

本企画書では、現行機能を整理したうえで、正式プロダクト化に向けたターゲット像、価値提案、機能要件、非機能要件、運用要件、KPI、ロードマップ、リスク対策を詳細に定義する。

## 3. プロダクトの背景

### 3.1 背景

お酒を楽しむユーザーは、飲んだ銘柄や味の印象を記憶しておきたい一方で、実際には以下のような問題を抱えやすい。

- 飲んだ銘柄名を後で思い出せない
- どこ産の酒が好みに合ったか整理できない
- 写真、味メモ、日付が別々に保存されていて振り返りにくい
- 一般的なメモアプリや写真フォルダでは検索性・一覧性が低い
- 日本酒やワインは産地と味の関係性が重要だが、通常のログでは地理的な文脈が失われやすい

### 3.2 市場・ニーズ仮説

SipQuest が狙うニーズは、飲酒体験を「消費」で終わらせず、「蓄積」と「再発見」に変えることである。対象は大規模な B2B 業務システムではなく、まずは個人の趣味・嗜好の記録用途である。

想定ニーズは以下の通り。

- 日本酒やワインを学びながら記録したい
- 店頭や旅行先で飲んだ銘柄を後から見返したい
- 好みの傾向を産地軸で把握したい
- SNS 投稿よりも、まずは自分のための私的な記録を残したい
- スマホで素早く使え、アプリインストールの手間が小さいことを重視したい

## 4. 解決したい課題

SipQuest は次の課題を解決する。

### 4.1 ユーザー課題

- 記録したいが入力が面倒で継続しない
- 写真だけ残っていて、味の記憶や感想が残らない
- 検索しても「どの地域の酒だったか」が分からない
- 同じような銘柄を試していても自分の傾向を把握できない
- お気に入りの酒を再購入したいが、記録の所在が散らばっている

### 4.2 プロダクト課題

- 一般的なログアプリとの差別化が弱いと継続率が上がりにくい
- ワイン・日本酒・ウイスキー系の情報は産地起点で整理されることが多く、通常の一覧 UI だけでは体験価値が出にくい
- モバイルでの即時入力と振り返りの両立が必要

## 5. プロダクトビジョン

SipQuest のビジョンは、「飲んだ一杯を、地図上の記憶として蓄積する」ことである。

記録対象を単なる商品情報としてではなく、以下を含む体験データとして扱う。

- いつ飲んだか
- 何を飲んだか
- どこ由来か
- どう感じたか
- どんな見た目だったか

これにより、SipQuest は単なる飲酒メモではなく、「個人の味覚履歴を地理とともに探索するジャーナル」として成立する。

- 地図ベースの振り返り体験
- 酒類ごとに日本地図と世界地図を切り替える発想

- ローカルファーストに近いプライベートな使い心地

## 10. 目指すプロダクト像

SipQuest を正式なプロダクトとして育てる場合、以下の状態を目指す。

### 10.1 あるべき姿

- スマホで数十秒以内に記録できる
- 数か月後でも銘柄・産地・味がすぐに見返せる
- 地図ベースで自分の嗜好傾向が可視化される
- データが安全に保存され、端末を変えても継続利用できる
- ライトユーザーでも使え、深く楽しみたいユーザーには拡張価値がある

### 10.2 プロダクトポジション

- 記録アプリであり、レビュー SNS とは異なる
- 個人利用中心だが、将来的には共有・推薦・コミュニティ機能を足せる
- 趣味のログと軽い学習支援の中間に位置する

## 11. 主要ユースケース

### 11.1 新しい一杯を記録する

1. ユーザーが新規記録画面を開く
2. 飲んだ日、酒類、銘柄名、産地、味メモを入力する
3. 必要に応じて写真を添付する
4. 保存する
5. 詳細画面に遷移し、内容を確認する

### 11.2 過去の記録を探す

1. 一覧画面を開く
2. 銘柄名、産地、味メモのキーワードで検索する
3. 候補から該当記録を選択する
4. 詳細画面で再確認する

### 11.3 産地から振り返る

1. ホーム画面で日本地図または世界地図を表示する
2. 地域をタップする
3. 地域に属するログ一覧を見る
4. 気になる記録を開いて詳細を見る

### 11.4 記録を更新する

1. 詳細画面から編集へ進む
2. テキストや日付を修正する
3. 必要なら写真を追加する
4. 更新後の内容を確認する

### 11.5 記録を整理する

1. 不要な記録を開く
2. 削除を実行する
3. 関連写真ファイルも削除される

## 13. 機能要件

本節では、正式プロダクト化を前提に、現行実装を含む機能要件を定義する。

### 13.1 記録管理機能

#### FR-01 記録作成

- ユーザーは飲酒記録を新規作成できること
- 必須項目は、飲んだ日、酒類、銘柄名であること
- 任意項目として、産地、味メモ、写真を入力できること

#### FR-02 記録編集

- ユーザーは既存記録を編集できること
- 編集時に既存情報を初期表示すること
- 写真追加時は既存写真を維持したまま登録できること

#### FR-03 記録削除

- ユーザーは記録を削除できること
- 記録削除時、関連写真も後処理で削除されること

#### FR-04 記録詳細閲覧

- 個別記録の全項目を表示できること
- 写真が複数ある場合は一覧表示できること

### 13.2 検索・閲覧機能

#### FR-05 キーワード検索

- 銘柄名、産地、味メモを横断検索できること
- 検索条件を URL クエリとして保持できること

#### FR-06 地図探索

- 酒類に応じて日本地図または世界地図で閲覧できること
- 地域ごとの記録件数を表示できること
- 地域を選択すると、その地域の記録一覧を表示できること
- 未分類データも選択・閲覧できること

#### FR-07 一覧カード表示

- 一覧では最低限、酒類、銘柄名、飲んだ日、産地、味メモ抜粋、写真サムネイルを表示できること

### 13.3 メディア機能

#### FR-08 写真アップロード

- 画像ファイルのみ受け付けること
- 1 ファイルあたり 10MB 以下とすること
- 安全な拡張子補正を行うこと

#### FR-09 写真保存

- 保存時は一意なファイル名を付与すること
- 保存先はアプリ配下のアップロードディレクトリとすること

### 13.4 モバイル利用機能

#### FR-10 PWA 対応

- ホーム画面に追加できること
- アイコン、テーマカラー、起動情報をマニフェストで提供すること
- サービスワーカーにより最低限のアセットキャッシュを持つこと

### 13.5 将来拡張機能

以下は現時点では未実装だが、正式プロダクト化で優先検討すべき機能である。

- アカウント登録 / ログイン
- クラウド同期
- CSV / JSON エクスポート
- データインポート
- お気に入り登録
- 飲酒回数ランキング
- タグ付け
- 店舗記録
- 評価スコア
- 香り・甘辛・酸味などの構造化入力
- 共有リンク
- レコメンド
- リマインド通知
- バックアップ / 復元

## 14. 非機能要件

### 14.1 ユーザビリティ

- スマートフォン片手操作でも主要導線を完結できること
- 入力項目は少なく、学習コストが低いこと
- 一覧・詳細・新規作成が迷わず遷移できること

### 14.2 パフォーマンス

- 初回表示は軽量であること
- 一覧検索は体感上すぐ反映されること
- 地図切替や地域選択に大きな待ちが発生しないこと

### 14.3 可用性

- 個人利用前提ではあるが、日常記録を阻害しない安定性を持つこと
- PWA 利用時に最低限の静的アセットが安定して読み込めること

### 14.4 セキュリティ

- 画像アップロード時に MIME 種別を検証すること
- ファイルパスがアップロードルート外へ逸脱しないこと
- 将来的にクラウド化する場合は認証・認可設計を追加すること

### 14.5 データ保全

- 将来的にバックアップ、エクスポート、端末移行をサポートすること
- 現行ローカル構成では、端末故障・誤削除が最大リスクであることを利用者に明示すること

### 14.6 保守性

- 画面、コンポーネント、データアクセス層の責務が明確であること
- データモデル追加に耐えられる設計であること

## 15. 情報設計とデータ設計

### 15.1 データモデル

#### DrinkLog

- `id`
- `drankAt`
- `drinkType`
- `brandName`
- `origin`
- `tasteNote`
- `createdAt`
- `updatedAt`

#### DrinkPhoto

- `id`
- `drinkLogId`
- `storagePath`
- `mimeType`
- `fileSize`
- `createdAt`

### 15.2 データの意味づけ

- `drankAt`: 飲酒日
- `drinkType`: 地図モードや集計軸に使うカテゴリ
- `brandName`: 主検索キー
- `origin`: 地域分類の主要元データ
- `tasteNote`: 自由記述の感想
- `photos`: 振り返り時の視覚情報

### 15.3 地域分類ロジック

現行では、`origin` に含まれる文字列キーワードで地域を推定している。

- 日本地図: 北海道、東北、関東、中部、関西、中国、四国、九州・沖縄
- 世界地図: 北米、南米、欧州、中東・アフリカ、アジア、オセアニア

### 15.4 今後の改善余地

- 産地を自由入力だけでなく選択補助付きにする
- 地域、都道府県、国、醸造所などの構造化を進める
- 曖昧な産地入力を正規化する辞書を持つ
- 酒類ごとに適切な地域分類ルールへ分ける

## 16. システム構成

### 16.1 現行技術スタック

- フロントエンド: Next.js App Router
- 言語: TypeScript
- UI: React
- データアクセス: Prisma
- DB: SQLite
- PWA: Manifest + Service Worker

### 16.2 現行アーキテクチャ概要

- 画面は App Router のサーバーコンポーネント中心
- データ更新は Server Actions で実施
- DB アクセスは Prisma Client で統一
- 写真はローカルファイルとして保存
- 地図探索 UI はクライアントコンポーネントで提供

### 16.3 将来アーキテクチャ案

- DB を SQLite から PostgreSQL などに移行
- 画像保存をローカルからオブジェクトストレージへ移行
- 認証基盤を追加
- デバイス間同期 API を追加
- 分析イベント収集基盤を追加

## 17. 競争優位性と差別化戦略

### 17.1 競争優位性

- 地図から辿る体験が主導線になっている
- お酒の種類と産地文脈を自然に結びつけている
- 個人記録に特化した軽さがある
- PWA によりネイティブアプリに近い導入しやすさを持つ

### 17.2 差別化の方向性

- 一覧重視アプリではなく、探索重視アプリとして訴求する
- 学習・コレクション・思い出保存を同時に満たす
- 「何を飲んだか」だけでなく「どこ由来か」で価値を出す

- PWA インストール率

### 18.3 KPI の見方

- 継続率が低い場合は、入力負荷または再訪価値が不足している可能性が高い
- 未分類率が高い場合は、産地入力 UX または分類辞書の改善が必要
- 地図タップ率が低い場合は、差別化機能が十分伝わっていない可能性がある

## 19. 収益化の方向性

現行アプリは個人向け MVP であり、収益化実装は存在しない。正式プロダクト化を想定した場合、以下の選択肢がある。

### 19.1 フリーミアム

- 無料: 基本記録、検索、地図閲覧
- 有料: クラウド同期、バックアップ、複数端末利用、詳細分析、CSV エクスポート、無制限写真

### 19.2 サブスクリプション

- 月額または年額でプレミアム機能を提供
- コア価値はデータ保全と振り返り強化

### 19.3 提携モデル

- 酒販店、イベント、サブスク酒便との連携
- 産地や銘柄情報の拡充
- 推薦導線やキャンペーン掲載

### 19.4 留意点

- 収益化は記録継続価値が成立してから導入すべき
- 初期段階では有料化より継続率とデータ蓄積価値の検証が優先

## 23. 想定リスクと対策

### 23.1 データ消失リスク

- リスク: ローカル保存のみでは端末破損・削除に弱い
- 対策: エクスポート、バックアップ、クラウド同期を優先

### 23.2 地域分類精度リスク

- リスク: 自由入力の産地が分類されない、誤分類される
- 対策: 入力補助、辞書強化、構造化データ化

### 23.3 継続率低下リスク

- リスク: 記録入力が面倒で利用が続かない
- 対策: 必須項目を最小化し、後編集前提の UX にする

### 23.4 差別化不足リスク

- リスク: 単なるメモアプリに見える
- 対策: 地図体験をトップ導線として磨き込み、ブランドメッセージも統一する

### 23.5 ストレージ肥大化リスク

- リスク: 写真保存で容量が増大する
- 対策: 圧縮、サムネイル生成、容量上限、クラウドストレージ活用

## 24. 成功条件

SipQuest の成功条件は、単に記録機能があることではなく、以下が成立することである。

- ユーザーが気軽に記録を始められる
- 記録したデータを後から見返す価値が高い
- 地図 UI が継続利用の理由になっている
- データ保全への不安が小さい
- 「好みが見えてくる感覚」を提供できる

## 25. 今後の提案

直近で着手すべき優先事項は以下の通り。

1. データ保全施策の追加
2. 産地入力と分類精度の改善
3. 写真管理体験の改善
4. 利用状況を測る KPI 計測基盤の導入
5. 認証とクラウド同期の導入判断

## 26. まとめ

SipQuest は、飲んだお酒を単に記録するだけではなく、地図から再訪できる体験を核にした個人向け飲酒ジャーナルである。現行実装は、記録、検索、地図探索、写真保存、PWA という MVP の中核を既に備えている。一方で、正式プロダクトとして成長させるには、データ保全、産地の構造化、継続率改善、同期機能、分析基盤が重要な投資対象となる。

本企画の本質は、「一杯ごとの記憶を、地理と感想を伴う資産に変える」ことである。SipQuest はその方向性に十分な独自性を持っており、個人向け趣味アプリとして明確な育成余地がある。
